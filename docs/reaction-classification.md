# 文字起こし → 判定 → 塗り（実験）

2026-11-18のユーザー指定により `jadge/reaction-evaluator` をNode側へ組み込んでいます。2026-11-19 に提供者（ユーザー）の指定で 0.4.0 へ更新し、埋め込みモデルを Ruri v3 30m（q8）に替えています（AGENTS.md D-088）。判定結果と演出の対応は以下です。

| ライブラリの `level` | キー  | 塗り                                                  |
| -------------------- | ----- | ----------------------------------------------------- |
| 長い文章             | 1 / F | 回転ジャンプで着地し、通常インクを広く塗る            |
| 短い相槌             | 2     | 縮んでから大きくなる動きと、広い扇状の5滴・着地しぶき |
| 迷い                 | 3     | 通常クリックと同じ1発                                 |
| 除外                 | 4     | 発射・塗りを追加しない                                |

モーションの追加調整：F・1の飛び上がる高さは3.1から2.15、水平回転は3回から2回へ抑え、変形も小さくしました。2は約58%まで縮んで約140%へ跳ね返り、0.85の高さまで回転せずに跳び上がり、着地して元に戻ります。移動や接地判定ではなく、立方体の見た目の動きです。着地の星・ハート選択は画面から外し、旧形指定を受け取った場合も通常インクへそろえます。

通常のタップ・クリック／長押しによる塗りは保持しています。追加の実験として通常インクは初期状態で常時発射し、右下の「通常インク常時発射」でON/OFFを切り替えられます。潜航・必殺技中は従来の制限に従って停止します。相槌と通常インクの発射待ちは分け、2の跳躍中（約0.32秒）は通常インクの新規発射を止め、着地後に再開します。短いタップも1発を受け付けます。除外はその発話からの発射を止めるだけで、手動インクや歩行跡、既存の塗りには影響しません。

## 現在の判定ライブラリ

`vendor/reaction-evaluator-0.8.0-3f5772b8fa97.tgz` を取り込んでいます。0.8.0 では、9文字以上の発言は元の話に関係があるときだけ長い文章になります。元の話（発表者のエピソード）がないときは除外します。0.7.0 では、8文字以下の相槌でない短い発言（「〜ました」「〜ます」や「私は」「学校の」のような文の途中で切れた形）を除外します（相槌の例・「わかります」などの決まった言い方・聞き返しは除く）。0.6.0 では、発表者がロビーで入力したエピソードを元の話として使い、9文字以上でも話に関係ない発言（「2000円って書いてある」など）を除外します（関係あるか迷うときは迷い）。話に関係あるかは、元の話との近さと、除外の例より話に近いかを埋め込みだけで判定し、kuromoji は読み込みません。0.5.0 では、ひらがな・カタカナ・漢字を含まない入力（相槌の例「OK」「lol」「w」などを除く）と音声認識の誤りの決まった文（「ご視聴ありがとうございました」など）を、相槌らしさと比べずに除外します。意味のない音の並びとつなぎの声の組み合わせも除外の例として学習しています。0.4.0 からは埋め込みモデルを Ruri v3 30m（q8）へ替えて学習し直し、スコアの係数を5から12に上げました（「迷い」が減り、相槌か除外にはっきり分かれやすくなります）。元の話がない判定ではkuromojiを読み込みません。以下のルールは0.2.0からそのまま引き継いでいます。

- 「デザイン」「アイデア」「UI」などのプロダクト語を含む発言は、短くても長い文章。ただし、明確に除外される発言はライブラリの除外を優先。
- 「すげえ、マジか天才」のように、既知の相槌を組み合わせた発言の識別。
- ユーザーの追加指定により、アプリでは相槌のセットを一つにせず、ライブラリの辞書と分解処理で各相槌に分け、各々を判定する。「すげえ」「まじか」「天才」の3件など。単なる読点分割は行わず、普通の説明文は一つのまま扱う。

分解部分の表記はライブラリの正規化後（ひらがな等）になる場合があります。元の文字起こし全文は保持して表示します。APIは一度の通信で各部分の結果を返し、画面では各分類を表示して、それぞれの分類で順番に塗ります。全部分を一律に相槌に決め打ちしません。演出待ちは最大32件・15秒までです。

## ユーザーネーム

参加者の表示名を含む発言は、モデルに優先して短い相槌（2）にします。元の話に名前があるだけでは適用しません。参加者名は自動で使い、検証用の追加名は「相槌にするユーザーネーム（追加）」で入力できます。追加名はカンマ・読点・改行で区切ります。

全角半角・英字大小・カタカナ／ひらがなをそろえた部分一致です。空名や正規表現による一致は使わず、読みや略称を推測しません。名前だけで決まる発言は埋め込みモデルを準備・推論せず返せます。分割する発言では各部分でこのルールを適用します。名前リストと元の話は発話ごとに固定します。

## 試し方と表示

`npm run dev` で起動し、`?dev` の検証画面の「マイク・文字起こし」を開きます。「判定モデルを準備」で初回約45MBを取得し、以後はキャッシュを使います。マイク開始時にも先に準備を始めます。

マイクでの文字起こし、または「元の話・ユーザーネーム・文字で試す」から文章を入力できます。元の話は任意です。「文字起こし結果」の各文章と「判定 → 塗り」に判定中・分類・失敗／中止を表示します。連続相槌は各部分のラベルも表示します。「確定後の判定待ち」は確定入力を受けてから判定を得るまでのブラウザ側計測で、音声認識自体の待ち時間を含みません。

マイク・文字起こしパネルの開閉と、右上の検証説明の折りたたみは保持しています。閉じる・ページを離れると先読み・未処理の判定と塗り待ちを中止します。

## 遅延の削減

- マイク開始と同時にNodeのモデルを先に準備し、試しの1回を計算して初回推論を温める。
- 相槌らしさと除外の判定で同じ発言の埋め込みを二重計算していたため、同じ計算中のPromiseと結果を共有する。埋め込みは最大128件・60秒、判定結果は最大64件・30秒。失敗はキャッシュしない。モデル・量子化・しきい値は変えない。
- ブラウザの先読みは置き換え可能な最新候補を使い、結果は最大16件・完了後10秒。古い先読みは中断し、確定処理を優先する。分割結果も一括して再利用する。
- 相槌インクの飛行は約0.37秒から約0.266秒に短縮。相槌の発射間隔は0.32秒、通常インクは従来どおり0.17秒。両者を別々に管理する。

同じ連続相槌を手入力で再判定したブラウザ確認では、確定後の判定待ち7msを観測しました。これはキャッシュが使えた時の一例で、発声からの総遅延ではありません。

変更後のローカルAPI単体では、更新モデルを使う短い入力は約7〜18ms、名前一致は約1ms、同文の再判定は約0.3〜0.5msを観測しました（連続相槌の分割追加前の参考計測）。音声認識・通信・描画を含む保証値ではありません。Web Speech側の認識・確定待ち時間はアプリから自由に設定できないため、遅延をゼロにはできません。

## APIと保持

- `POST /api/reaction/prepare`、`GET /api/reaction/status`: 準備・状態確認。
- `POST /api/reaction/evaluate`: `{ source, reaction, userNames? }`。反応は1〜500文字、元の話は最大2000文字、名前は各1〜20文字・最大32件。入力不備400、過負荷429、判定失敗503。返答はHTTPキャッシュしない。
- 単一結果は `{ level }`。分割時は `{ level, segments: [{ text, level }, ...] }`。分割時の `level` は旧クライアント向けの先頭結果で、現クライアントは各 `segments` の分類を独立して演出へ渡す。
- 不明な分類や失敗を仮の塗りに置き換えない。同じ文字起こしIDを重複確定しない。停止後の遅れた結果も塗らない。

Web Speechの音声外部処理は `web-speech-privacy.md` を参照。今回の低遅延化により、途中・確定した文字と任意の元の話・相槌判定用の名前をゲームのNodeサーバーへ送ります。埋め込み・形態素解析・判定はNode内で行い、文章を外部AI APIへ送る処理は加えていません。Nodeへ音声は送信しません。

音声・発話本文のログ、DB、ファイルは作りません。ブラウザの文字起こし・判定履歴、上記の計算キャッシュ、ライブラリの元の話キャッシュ最大500件・ペア解析キャッシュ最大50件は一時メモリを使います。ライブラリのキャッシュはプロセス終了まで残る場合があります。

## 残る検証

元ライブラリの38テストと、アプリの入力・分割・名前・先読み・中断・共有キャッシュ・塗り形状・動きのテストを実行しています。実マイクからの一連の精度・体感速度、多人数の実ネットワーク試合は別途確認が必要です。正式試合でのAPI認証・発表者照合は既存の手動塗りと同様に今後の統合範囲です。

## 途中認識からの相槌発射（2026-11-18）

「はいはいはいはい」は4回、「なるほどなるほど」は2回に分け、最初の1個が認識された時点で塗ります。完成した「はい」「なるほど」の並びは追加の待ち時間なし、それ以外は80msの先読みで、既知の相槌だけの判定結果を発射します。通常文は確定後です。「はい」「なるほど」は埋め込みモデルの準備・計算を待たない明示的な高速ルールです。

APIの単一・分割結果には任意の `streamable: true` を追加しました。途中と確定に同じ発話IDを付けて既発射の部分を追跡します。途中更新では増えた部分だけを発射し、確定後は既発射の接頭辞を除いた残りを判定します。確定後に届く途中結果は発射しません。例えば「はい」の発射後に「はい、僕も行った」と確定したら、残りの文を追加判定します。途中認識が後で修正されても既発射の塗りは残ります。

「元の話・ユーザーネーム・文字で試す」の「相槌の途中入力を試す」から、実マイクを使わずに途中発射と確定時の重複防止を検証できます。目標は発話終了から0.5秒以内ですが、Web Speech側の認識待ち時間はアプリで制御できず、実マイクの総遅延は未検証です。表示の「確定後の判定待ち」は音声認識とインクの飛行・演出待ちを含みません。

今回の検証：全120テスト、型チェック、ビルド、静的検査が成功。ブラウザで「はい」1個目の途中発射、反復4回／2回、確定後の重複防止、相槌に続く文の追加判定を確認。ローカルAPIの参考計測は「はい」20ms、反復は2ms。実音声の総遅延ではありません。
